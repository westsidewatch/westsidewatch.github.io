# 数片 / PARADISO — Restoration ledger (2026-11-22)


## 起源與不可遺失的技術基準

**整項反向搜尋／去廣告引擎的起點，是對 `https://www.mvffm.net/drama/420952/` 這個具體播放站點的逆向分析。** 不得將起點誤寫成 Scrapling、Firecrawl 或任意單部劇搜尋。其真正有價值的原始技術，是在**實際瀏覽器**觀察 `mousedown`、`shown_at`、`window.open`、臨時 iframe、第三方分頁和網路媒體請求的事件關聯，並區分網站／播放器廣告與 M3U8 或影片本體的廣告。

**防退化基準：** 永久保留 [mvffm 原始反向工程](https://github.com/weber87na/mvffm-redirect-guard) 的技術指紋與 [本站鑑識紀錄](MVFFM-AD-ORIGIN-2026-11-22.md)；`scripts/shupian_recovery/mvffm_live_reverse.py` 是新增加的動態**觀測**入口，`media_ad_origin.py` 是分層判讀入口。二者不可互相替代。原 MV3 防護工具仍是外部獨立工程，未證明已集成至本站；須以瀏覽器 smoke + 真正網路／播放 A/B 驗收，才可稱恢復完整能力。四關閉環要求繼續有效。

## 第一條｜工程目的與最高優先級（不可更改）

**本工程的目的，是製作「搜尋、去廣告的片源引擎」。影視網站不是獨立產品目標，而是用來實際檢驗這個核心引擎好不好用的實驗結果。所有工作，必須圍繞核心引擎展開。**


**核心引擎的最終輸出：** 對每部待查作品搜尋並識別所有可用候選來源，優先找出真正能起播、內容與集數相符、沒有廣告干擾的乾淨 `m3u8`／HLS，以及其他支援格式的媒體來源（例如 MP4、DASH）。「找到來源」必須是有實際媒體地址及驗證證據，不是影視介紹、影視平台首頁或單純海報。**找到多少，取決於真實結果，不得只取第一條就停止，也不得捏造存在的來源。**

**核心算法持續升級義務：** 一旦發現新片源命中率、有效 URL 比例、逐集識別、播放穩定性或廣告干擾過濾結果不足，立即開展「多雷探索」：檢視原有程式與編輯手冊、研究成熟開源爬蟲與瀏覽器網路分析工具，先在受控樣本上實測，優化反向解析／資料擷取、去重、來源評級與錯誤回退，再經回歸測試後接入核心引擎。禁止用「找不到」直接結束工作，亦不可無驗收就替換核心。測試遵守站點存取規則，不繞過 DRM 或保護機制。

**算法量化指標：** 每次實驗保存搜尋詞、搜尋來源數、命中數、真正媒體 URL 數、成功解析的季集數、HLS 主子清單及分段檢查結果、首幀／持續播放結果、廣告標記／廣告干擾、失敗分類、來源更新時間；以數據決定是否採用新算法。

**候選工程路徑（2026-11-22 多雷探索資料）：** Scrapling 可用於自適應選擇器與並發擷取；Playwright 的網路事件／response 監測可用於有動態載入的允許存取頁面；HLS `EXT-X-DATERANGE`、SCTE-35 等標記的解析遵循 RFC 8216 及相關規格。此處為**候選技術方向**，未經本工程實測不得稱為已接入。
- Scrapling: https://scrapling.readthedocs.io/en/latest/
- Playwright: https://playwright.dev/python/docs/network
- HLS: https://www.rfc-editor.org/rfc/rfc8216



1. **第一順位：片源搜尋引擎。** 以作品名稱、原名、年份、季數、集數進行來源發現，解析來源頁與逐集媒體地址，保留來源、匹配及可追溯結果。搜尋能力不得被停用、刪除、降級或以人工片單取代。
2. **第二順位：去廣告與來源品質。** 識別廣告片頭、片中插播、浮層、跳轉及疑似內嵌廣告；區分可技術過濾的外掛廣告與無法安全移除的影片內嵌內容；驗證是否能實際解碼、是否為正確作品與集數。不得繞過 DRM 或對第三方媒體擅自作公開再分發。
3. **第三順位：影視網站作為測試台。** 「数片」的搜尋、海報、片單、集數、播放器及實際觀看體驗，是用來證明引擎搜尋與去廣告能力的前台實驗結果；不得為了把網站填滿而新增無片源的作品，更不得拿美術排版或虛假播放按鈕充當引擎成果。
4. **所有後續工作以引擎為中心。** 優先恢復原始來源發現模組及自動測試，串接去廣告與播放驗證，再用網站做端到端驗收。任何視覺、編輯與部署工作必須服務這條主線，不可倒置先後順序。
5. **工程驗收的第一指標是引擎效果，不是卡片數量。** 必須記錄真實搜尋查詢、來源命中及有效率、逐集匹配、去廣告結果、首幀成功率、播放穩定性、失敗原因；網站的可見、可搜、可播是最終整合測試。

**每一次任務必須完成的四關閉環：①片源搜尋與逐集解析 → ②去廣告與品質判定 → ③實際播放驗證 → ④「数片」網頁落地及端到端驗收。** 這四關**不是**四項分開做完的大工程，也**不是**可以長期停留在「核心算法升級」的工作階段。每一次找片源、修復來源、改進算法、增加作品，均須在**同一輪任務**依次完成四關，直至網頁可見、功能可用、真實驗收通過，才算交付完成。

**四關的完成定義：**
- **① 搜尋：** 本輪目標作品／季集有實際搜尋輸入、來源發現與逐集匹配記錄；不得以已有片單冒充新結果。
- **② 去廣告：** 對找到的媒體來源做廣告標記、網頁干擾、品質及可用性檢查，記錄過濾和判定結果。
- **③ 播放：** 實際測試解析、首幀、拖曳／跳轉、持續播放及集數內容匹配，保留成功或失敗證據。
- **④ 網站落地：** 將該輪已驗證的結果整合進「数片」正式網站，核對作品、海報、集數、來源狀態、播放器及桌面／手機實際頁面。**這是每輪工作的交付終點，不是可選的後續美化工作。**

**回退規則：** 某一關不合格，回到需要修正的前一關，必要時在當輪啟動「多雷探索」改善核心算法，再重新經過後續各關直至網站落地。**不得把一輪未通過第四關的工作報稱已完成。** 外部來源確實不可用時，記錄客觀阻塞與已做的測試，不捏造可播放結果。

**本條優先於其他恢復清單、歷史資料與 UI 設計說明。**


## 第一輪搜尋策略｜多雷探索所得：先找對入口，再擴大搜查

**固定四個動態搜尋桶：** 最新美劇／英劇、日本動漫、經典電影、福音影視。每一輪都同時搜索四類，不以單一劇名取代全面搜尋。每類查詢同時包含繁簡體、英文、近兩個年份（適合最新作品）、模糊別名及無片名的分類目錄遍歷；必須去重及逐集保留全部來源。

**已核對的關鍵 API 事實：** 官方 MacCMS v10 Provide 介面中，`ac=list` 為高效片目／分類發現，通常只含 ID、名稱、分類與時間；這類列表**不直接給 `vod_play_url`**。因此最佳的兩段式入口是 `ac=list&pg=...`（必要時帶 `t` 分類）找候選 ID，然後用 `ac=detail&ids=...` 取得 `vod_play_from`、`vod_play_url` 和集數，不得因 list 內缺少片源就記作零結果。分類 ID 應從各站返回的 `class`／分類資料辨識，不能假定不同站分類 ID 一樣。

**演算法方向（優先級）：** (1) 來源站目錄與分類探索；(2) 分頁片目 ID → 詳情媒體地址；(3) 各語言及作品別名模糊搜尋；(4) 依觀測命中、重複率、解碼成功率自動調整來源優先級、停用失效接口的當輪重試（保留原始來源配置）；(5) 標準 API 無效時，才在允許存取頁面採用 Scrapling 自適應選擇器／Playwright 網路事件解析；(6) 按官方 HLS 標記及實際解碼做去廣告與品質驗證。

**工程完成口徑：** API 查詢紀錄、真實候選、廣告判定與播放器測試、正式網站落地四關缺一不可。搜尋模組與測試代碼提交只算「第一關進展」，不等於本輪完成；網絡受阻時須留下具體錯誤和未達標狀態，不能杜撰網頁成果。

### 固定工程鏈條（任何施工不得省略發現步驟）

`作品／集數識別 → 可用來源目錄查詢 → 解析供應商與逐集地址 → HLS 主／子清單驗證 → 分段及解碼 → 完整集數核對 → 廣告與播放體驗檢查 → 帶證據的片庫記錄 → 正式頁面核對`
