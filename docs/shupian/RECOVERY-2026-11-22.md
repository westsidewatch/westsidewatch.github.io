# 数片 / PARADISO — Restoration ledger (2026-11-22)


## 第一條｜工程目的與最高優先級（不可更改）

**本工程的目的，是製作「搜尋、去廣告的片源引擎」。影視網站不是獨立產品目標，而是用來實際檢驗這個核心引擎好不好用的實驗結果。所有工作，必須圍繞核心引擎展開。**

1. **第一順位：片源搜尋引擎。** 以作品名稱、原名、年份、季數、集數進行來源發現，解析來源頁與逐集媒體地址，保留來源、匹配及可追溯結果。搜尋能力不得被停用、刪除、降級或以人工片單取代。
2. **第二順位：去廣告與來源品質。** 識別廣告片頭、片中插播、浮層、跳轉及疑似內嵌廣告；區分可技術過濾的外掛廣告與無法安全移除的影片內嵌內容；驗證是否能實際解碼、是否為正確作品與集數。不得繞過 DRM 或對第三方媒體擅自作公開再分發。
3. **第三順位：影視網站作為測試台。** 「数片」的搜尋、海報、片單、集數、播放器及實際觀看體驗，是用來證明引擎搜尋與去廣告能力的前台實驗結果；不得為了把網站填滿而新增無片源的作品，更不得拿美術排版或虛假播放按鈕充當引擎成果。
4. **所有後續工作以引擎為中心。** 優先恢復原始來源發現模組及自動測試，串接去廣告與播放驗證，再用網站做端到端驗收。任何視覺、編輯與部署工作必須服務這條主線，不可倒置先後順序。
5. **工程驗收的第一指標是引擎效果，不是卡片數量。** 必須記錄真實搜尋查詢、來源命中及有效率、逐集匹配、去廣告結果、首幀成功率、播放穩定性、失敗原因；網站的可見、可搜、可播是最終整合測試。

**優先級固定：片源搜尋 → 去廣告與品質判定 → 播放測試 → 网站呈現與實驗驗收。** 本條優先於本文件其餘恢復清單、歷史資料與 UI 設計說明。

## P0 事故復盤｜核心「片源發現」被截斷（2026-11-22；不可再犯）

**事故性質：恢復工程重大失職。** 本工具的核心用途是「發現影片來源」，不是僅有片單、海報與驗收工具。工程對話已多次明確要求恢復整條鏈路，任何人不得再把只剩 HLS 測試的局部模組稱為「完整找片源引擎」。

### 核查過的原始證據（區分檔案存在與實際運行）

2026-11-20 版 `paradiso_engine_v1.zip` 已打開檢查。壓縮包含 `paradiso_engine/engine.py`、`providers.json`、`tests/test_engine.py`、`data/hls_structural_queue.json` 和測試素材。

- 原始 `engine.py` 的 `sources` CLI **確實存在**；它從 `providers.json` 讀取 6 個來源 API，按搜尋詞發出 `?ac=detail&wd=...` 查詢，並透過 `play_groups()` 解析 `vod_play_from` 與 `vod_play_url` 中以 `$$$`、`#`、`$` 分隔的供應商、集數及 HLS 地址。
- 原引擎另有 `audit`、`rank`、`scan-video`、`merge` 命令，用來檢查 HLS 結構、來源採樣、影格和清單合併。
- **重要更正：** 原壓縮包 `README.md` 明確寫著它是「independent importer/validator not yet installed in the live private Sites project」。因此，不能宣稱這個 ZIP 的 `sources` 曾在以前的公開網站正式上線；此前「之前之所以找到全部來源就是因為該工具已部署」的說法沒有充分證據。
- 目前 GitHub `scripts/shupian_recovery/legacy_engine_core.py` 的函數只涵蓋 `validate_public_url`、`parse_hls`、`permit_import`、`merge_catalog`、`scan_video_frames`、`rank_providers`，**缺少 `sources`、`play_groups`、`fetch_text`、`audit_url`**。代碼注釋甚至註明 `provider discovery layer ... intentionally not enabled`。這是我在恢復時實際縮減了核心能力的直接證據。
- `scripts/shupian_source_audit.py` 是「對已知 URL 的驗證」，**不是發現新 URL**。我曾把它錯當片源恢復的主工作，導致繼續產生「有片單、無片源、無播放」。
- 已保存的 12 條歷史候選證明曾經有過來源記錄，但不等於當前地址全部可用。技術審查清單現已包含這 12 條候選；不等於已恢復搜尋新作品的完整引擎。

### 固定工程鏈條（任何施工不得省略發現步驟）

`作品／集數識別 → 可用來源目錄查詢 → 解析供應商與逐集地址 → HLS 主／子清單驗證 → 分段及解碼 → 完整集數核對 → 廣告與播放體驗檢查 → 帶證據的片庫記錄 → 正式頁面核對`

**發現與驗證是兩種不同能力**。發布前需要明確區分「搜尋有結果」「找到媒體地址」「分段可讀」「播放器成功」「完整作品可用」，不得用前者冒充後者。新加入的作品若只有標題、海報和影視介紹，必須列作「片目」，不能列作「可播放」。

### 防止再次停用的工程規則

1. 恢復工程必須先檢查原始完整工具的命令、設定、資料結構和歷史輸出，再決定如何移植；**不許自行刪減／停用核心功能而不向使用者明確說明**。
2. 所有新版本必須有可測試的「來源發現入口」、可追查的候選證據和獨立的片源驗證階段。不得只提供 `audit` 指令、片單 JSON 或外部平台連結。
3. 保留原始壓縮包、歷史驗收與來源報告，新增程式不覆寫歷史資產。對不明來源不得編造播放成功報告，也不得繞過 DRM 或將未獲准分發的受版權保護影片公開上線。
4. 測試標準為：**發現入口存在且能接受作品／季集搜尋 → 返回有可追查來源的結果或清楚的零結果 → 候選與正片播放狀態分離 → 逐集播放結果可核對 → 正式網站瀏覽器驗收**。
5. 任何聲稱「找片源功能已修好」，必須提供**當次真實查詢與實際結果**；僅有提交成功、CI 配置或舊檔案存在，不算完成。任何聲稱「正式影院可播」，必須有當次實際瀏覽器播放結果。
