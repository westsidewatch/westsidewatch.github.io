# Doré Design Knowledge Lab

Status: part of Doré Coordination Hardening 1.0

Purpose: turn external design work into executable, tested, provenance-aware design knowledge instead of a passive asset library.

## Learning loop

Discover -> verify source/license/maintenance -> understand architecture and design advantage -> reproduce as isolated executable story -> compare with Westside needs -> test responsive/accessibility/visual behavior -> promote useful patterns -> record rejection/adoption evidence -> re-evaluate when needed.

## Three maturity layers

- Research: faithful studies of external patterns; never assumed approved.
- Candidates: reproduced and tested patterns that may fit Westside.
- Westside Core: explicitly adopted components/tokens/patterns safe for Doré Design and production reuse.

## Initial study queue

1. Existing Doré trials: Framesmith MCP, OpenPencil, Penpot AI/design workflows. Re-read prior evidence; do not assume earlier winners remain best.
2. Storybook: isolated stories, docs, interaction/accessibility/visual regression as the executable knowledge workbench.
3. GrapesJS: blocks, Style Manager, Layer Manager, Asset Manager, local/remote storage; study editor architecture, not visual style.
4. Plasmic: codebase integration, components/variants/slots, Figma-to-DOM/CSS import, content guardrails; study design-to-code architecture.
5. Puck ecosystem: React-component visual page building; study component registry and constrained page composition.
6. Figma/editorial templates and strong contemporary editorial sites: study hierarchy, typography, grids, responsive transformations, navigation, image treatment, motion and composition. Copy/fuse principles only when provenance/license allows; otherwise reproduce the underlying design principle, not protected assets.

## First executable pattern families

- EditorialHero
- Masthead
- JournalCard (5:8 variants)
- ScriptureBlock
- SectionNavigation
- Gate/Threshold CTA
- ReadingProgress
- ResponsiveEditorialGrid

Every study must record: source, date checked, license/usage status, what is good, what is weak, what can be reused, what must not be copied, responsive behavior, test evidence, Westside fit, and current disposition.

## Hardening invariant

A learning task is not PASS merely because code was generated. It must leave reproducible evidence and a runnable story/test or an explicit rejection record. Product monitor and coordination receipt must distinguish transport, execution, learning acceptance, and product acceptance.
