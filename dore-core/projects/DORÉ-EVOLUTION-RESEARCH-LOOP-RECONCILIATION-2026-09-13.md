## Reconciled interpretation

### 1. Doré Evolution is permanent Core work

`PROJECT.md` defines Evolution as the permanent capability-acquisition reflex:

`goal → attempt → observe → detect gap → research → equip → execute → verify → learn → transfer`.

This is correctly classified `CORE/CONTINUOUS / ACTIVE_PARALLEL`; it has no ordinary terminal completion date. Product work provides transfer evidence, but feature count is not its success metric.

`SELF-EQUIPPING-EVOLUTION.md` independently expresses the same durable direction at a broader equipment-governance level: Doré should increasingly detect capability gaps, inspect current equipment, research alternatives, sandbox/test candidates, adapt or compose them behind Doré-owned replaceable interfaces, verify them in real work, retain provenance/evidence, and later reuse the capability with declining human procedural involvement.

This is not a second Evolution architecture. It is governing doctrine for the same canonical workstream.

### 2. Foundational learning principles govern Evolution rather than compete with it

`DORÉ-FOUNDATIONAL-LEARNING-PRINCIPLES-v1.md` establishes the higher-order rules that Evolution must inherit:

- Great Commission is the governing purpose;
- capability must be earned through real work and later transfer, not exposure alone;
- completed projects and old products remain part of one living portfolio;
- engineering, research, external-AI consultation and self-improvement are capabilities in service of mission rather than identities;
- durable lessons must be persisted and near-duplicate principles should be extended/reconciled instead of proliferated;
- self-modification remains evidence-based, auditable and bounded by governance/safety.

Classification: `CORE/CONTINUOUS / GOVERNING LEARNING DOCTRINE`, not a separate project or graduation token.

### 3. 「多雷探索」 is an invocation alias, not a separate architecture

`DORÉ-EXPLore-TRIGGER-v0.1.md` is a human/automatic trigger contract for the Open Research Micro-Loop. It should not be represented as another product or another control plane. Its durable value is semantic: the phrase invokes the existing constitutional research policy and bounded Doré-fit filter.

Classification: `CORE SUPPORT / INVOCATION CONTRACT`.

### 4. Open Research Micro-Loop is a valid operating specification, not a completed autonomy claim

The micro-loop defines bounded 1–3 wave research, Memory freshness checks, USE/ABSORB/EXPERIMENT/WATCH/REJECT disposition, resource discipline, and required evidence return. The September 5 research packet demonstrates that the method can produce a concrete Doré-fit decision from a real research need.

However the loop's own acceptance contract requires a real Doré need to trigger the entire path through evidence return to Memory/Registry. The reviewed evidence does not independently prove automatic triggering, duplicate-search avoidance, Capability Registry return, or blind reuse across materially different domains.

Classification: `ACTIVE / IMPLEMENTED METHOD + UNKNOWN_NEEDS_EVIDENCE` for autonomous end-to-end use.

### 5. The “autonomous evolution last layer” research decision is historically complete

`2026-09-05-autonomous-evolution-last-layer.md` completed a bounded architecture/research decision and selected a thin native pattern:

- macOS `launchd` for on-demand wake;
- Python stdlib `sqlite3` for durable wake state;
- isolated candidates plus deterministic verifier gates;
- Git primitives for versioned candidate promotion where code is involved;
- no permanent research daemon and no heavyweight workflow framework by default.

As a research/design milestone this is `VERIFIED_COMPLETE / RESEARCH DECISION`.

### 6. Later runtime evidence materially realizes part of that design

Checkpoint 101 verifies the SQLite/WAL wake-runtime primitive: idempotent enqueue, transactional claims, leases, bounded retries, expired-lease recovery, verifier-gated promotion, backup preservation and durable promotion logging.

Checkpoint 105 verifies a dated local launchd activation with queue directories, 900-second interval, kickstart, durable SQLite state and a fresh smoke task reaching `passed`.

Therefore the September 5 architecture is no longer merely speculative. Its wake + durable-state + verifier-gated-promotion substrate has bounded implementation/deployment evidence.

### 7. Self-equipping doctrine adds explicit equipment-governance constraints

The Knowledge-layer document contributes durable rules that should remain attached to EVOLUTION rather than becoming separate workstreams:

- Doré-owned capability interfaces must remain distinct from providers/models/MCPs/databases;
- codebase/workspace knowledge, specialist roles, research reach/tool routing, isolated parallel workspaces, production pipelines/self-review and regenerable program maps are candidate equipment classes, not automatically adopted dependencies;
- a research note without a transfer experiment is incomplete for a viable candidate;
- provider failure cannot be inferred from an adapter failure or from not knowing the supported interface;
- deterministic retries must change hypothesis/adapter/tool/strategy rather than repeat blindly;
- terminal task state must trigger recovery/fallback or a genuine authority escalation rather than silently ending the parent goal;
- repeated shared failures should trigger reusable redesign/replacement rather than one-off patch accumulation.

These rules sharpen the acceptance criteria for future Evolution evidence but do not themselves prove autonomous equipment acquisition.

### 8. Whole autonomous Evolution cycle is still not complete

The evidence does **not** yet prove the full chain:

`automatic gap detection → fresh Memory check → bounded open research → candidate capability acquisition → isolated verification → canonical Memory/Registry admission → resumed parent goal → later blind transfer`.

Nor does it prove arbitrary production execution authority. Wake-runtime payload authority remains a separate safety boundary, and P01 remains unaffected.

The broader claim therefore remains `UNKNOWN_NEEDS_EVIDENCE`, consistent with `ME-007` and the existing EVOLUTION row.

## Duplication / supersession judgment

- `SELF-EQUIPPING-EVOLUTION.md` and `DORÉ-FOUNDATIONAL-LEARNING-PRINCIPLES-v1.md` are not duplicate projects. They are governing doctrine layers for the canonical CORE/EVOLUTION interpretation.
- Heavy always-on workflow engines as the default single-Mac Evolution substrate remain `REJECTED / NOT ADOPTED`, not active backlog.
- A permanent research daemon solely to keep Evolution alive remains `RETIRED AS DIRECTION / PROHIBITED BY CURRENT DESIGN`.
- Post-hoc rollback as the primary admission mechanism is `SUPERSEDED`; current doctrine is verify-before-promotion and keep unverified candidates outside canonical state.
- `多雷探索` must not be rediscovered as a separate product architecture; it remains an alias over the same Evolution research reflex.
- Candidate equipment classes named in the Knowledge document are research directions only until a real need, Doré-fit comparison and transfer acceptance justify adoption.

## Revisit trigger

Reopen this research decision if one of the following becomes true:

1. the single-Mac/native assumptions materially change;
2. multi-host/distributed execution becomes a real requirement;
3. launchd/SQLite no longer meets demonstrated reliability needs;
4. a mature replacement shows materially better behavior with acceptable weight;
5. real end-to-end autonomous research/admission evidence exposes a missing state or safety gate;
6. repeated product failures reveal that provider-neutral equipment routing, codebase knowledge, workspace isolation or production self-review requires a shared compulsory implementation rather than doctrine alone.
