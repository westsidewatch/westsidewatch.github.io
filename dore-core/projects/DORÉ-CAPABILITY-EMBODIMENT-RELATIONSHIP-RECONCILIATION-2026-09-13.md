## Reconciliation

### 1. One Doré / many faculties is current governing architecture

`DORE-CAPABILITY-EMBODIMENT-2026-09-05.md` and `DORÉ-SYSTEM-RELATIONSHIP-MAP-v1.md` converge on the same boundary: Doré Core is one persistent intelligence; products are bounded consumers/training environments; projects grow capabilities; providers/runtimes are replaceable execution substrate. Image, Design, Search, Research, Translation and Publishing are faculties/capabilities, not separate Doré identities by default.

Current classification: `CORE/CONTINUOUS / ACTIVE ARCHITECTURE`.

This is compatible with the current Product Registry and strengthens the existing `CORE`, `EVOLUTION`, `REFLEX` and `NERVOUS-SYSTEM` interpretations. It does not create a new workstream.

### 2. Sparse capability embodiment is doctrine, not a completed system milestone

The architecture defines a three-speed nervous system (`L0 deterministic`, `L1 semantic`, `L2 deliberative`), lazy capability loading, compact route manifests, typed artifacts, bounded active capability count, and downward compilation of repeated successful workflows.

The document itself explicitly says the architecture is not complete until measured. Its seven acceptance gates require, among other things, proof that non-visual tasks do not load visual skill bodies, dormant capability growth has negligible ordinary-run cost, repeated workflows compile downward, and resource telemetry exposes activation/model/latency/context/cache behavior.

This sweep found no single persisted artifact proving that entire acceptance contract. Existing Capability Registry, Reflex, A2A and Evolution milestones are real component evidence but must not be inflated into `CAPABILITY_EMBODIMENT_COMPLETE`.

Current classification: architecture `ACTIVE`; end-to-end embodiment acceptance `UNKNOWN_NEEDS_EVIDENCE`.

### 3. Product Registry is a real machine-readable companion, but not proof that every declared relationship is live

`product-registry.v1.json` concretely encodes the one-Doré principle, Core ownership, shared Scripture workspace, runtime planes, products, learning projects and hard invariants. It is therefore real implementation evidence for relationship declaration and architectural convergence.

However declarations such as product consumers, runtime ports, cross-product feeds and ownership boundaries are not automatically live runtime proofs. The registry must remain a contract/index whose claims are verified by product/runtime evidence.

Current classification: `ACTIVE / CANONICAL MACHINE-READABLE CONTRACT`.

### 4. Early Brand/Cloudflare architecture remains useful, but its old priority order is already superseded

`DORÉ-BRAND-OPERATING-ARCHITECTURE-v0.2.md` remains strong retained architecture for Doré identity, Library/Journal/asset roles, GitHub-vs-Cloudflare responsibility and human-governance boundaries. Its section-11 implementation order is already correctly indexed as superseded by `SR-004`.

`DORÉ-NEXT-PRODUCT-ROADMAP-v0.1.md` remains a historical continuation checkpoint. Its Cloudflare-first / Daily-Devotional-next priority order is already correctly superseded by `SR-002`; the current Master Register and persisted runtime state govern priority.

No new supersession entry is needed.

### 5. R2 Asset Architecture remains retained operating policy, with one evidence boundary

The durable architectural rules remain coherent with later verified R2/D1 asset migrations: GitHub for code/policy/versioned institutional truth and code-coupled binaries; R2 for growing editorial/media masters; one authoritative binary backend per asset; Asset Registry for identity/provenance/rights/usage; Workers/Pages Functions as bounded runtime adapters; Cloudflare is infrastructure, not Doré identity.

The embedded free-tier numeric allowances are design-time external assumptions. Existing `ME-004` correctly requires re-verification from authoritative provider documentation before those numbers are used for a present-day financial decision. No duplicate missing-evidence item is needed.

Current classification: `CORE SUPPORT / RETAINED OPERATING ARCHITECTURE`; pricing numbers remain time-sensitive evidence, not constitutional truth.

## Durable lessons

1. **Project boundary != intelligence boundary.** Separate repositories and runtimes may remain for engineering reasons without becoming separate Doré identities.
2. **Capability growth must not imply permanent context/runtime growth.** New abilities should be dormant until routed, with bounded activation and measurable marginal cost.
3. **Machine-readable registries declare truth boundaries; runtime/product tests prove them.** Registry presence is not product-pass evidence.
4. **Repeated workflows should compile downward only after verified reuse.** A design intention to become L0/L1 is not evidence that compilation happened.
5. **Historical roadmaps are provenance, not queue authority.** Current priority always comes from the Master Work Register plus persisted runtime state.
6. **Provider pricing is external state.** Architecture may preserve threshold policy while numeric allowances require fresh verification when financially consequential.
